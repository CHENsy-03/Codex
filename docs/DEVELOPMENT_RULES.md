# DEVELOPMENT_RULES.md

> 本文档定义项目日常开发、测试、审查和交付规范。
>
> 所有开发工作必须同时遵守项目根目录的 `AGENTS.md` 和 `docs/SYSTEM_ARCHITECTURE.md`。
>
> 本文档用于约束具体开发行为，不用于重新定义系统架构。

---

## 1. 开发基本流程

每个开发任务按照以下流程执行：

```text
读取 AGENTS.md
      ↓
读取 SYSTEM_ARCHITECTURE.md
      ↓
读取当前 TASK.md
      ↓
定位相关代码
      ↓
分析调用关系和数据流
      ↓
列出修改文件
      ↓
实施最小范围修改
      ↓
运行格式化和静态检查
      ↓
运行单元测试和集成测试
      ↓
检查 git diff
      ↓
输出修改摘要和风险
```

开始编码前必须明确：

* 当前任务目标；
* 修改范围；
* 不允许修改的内容；
* 输入和输出；
* 验收标准；
* 测试方式；
* 是否涉及兼容性；
* 是否涉及数据库或配置变更。

任务定义不清时，应先列出假设，不得擅自扩大范围。

---

## 2. 修改范围管理

每个任务只修改与当前需求直接相关的文件。

修改前应列出：

```text
文件路径
修改原因
预期变化
是否影响公共接口
是否需要新增测试
```

禁止：

* 将无关格式调整混入功能修改；
* 顺便移动大量目录；
* 顺便替换技术框架；
* 顺便升级全部依赖；
* 顺便重写正常工作的模块；
* 修改任务未涉及的公共接口。

确有必要进行额外修改时，应单独说明原因和风险。

## 3. Python 版本与代码风格

Python 版本应在项目配置中统一声明。

不同模块不得自行假设不同 Python 版本。

Python 代码必须：

* 使用明确、可读的命名；
* 为公共函数提供类型标注；
* 为复杂数据结构定义类型；
* 优先使用标准库和已有依赖；
* 使用项目统一格式化工具；
* 使用项目统一静态检查工具；
* 避免可变默认参数；
* 避免全局可变状态；
* 避免隐藏的导入副作用；
* 避免在模块导入时执行网络或数据库操作。

推荐使用：

* `snake_case`：变量、函数和模块；
* `PascalCase`：类；
* `UPPER_SNAKE_CASE`：常量；
* 下划线前缀：模块内部实现。

示例：

```python
DEFAULT_REQUEST_TIMEOUT = 30


class CrawlTask:
    pass


def normalize_url(raw_url: str) -> str:
    return raw_url.strip()
```

## 4. Python 函数设计

Python 函数应保持职责单一。

一个函数通常只完成一个阶段，例如：

* 构造请求；
* 下载页面；
* 解析标题；
* 清洗正文；
* 计算 Hash；
* 保存结果。

函数参数应尽量明确。

避免：

```python
def process(data, config, options, context, extra):
    ...
```

优先使用明确的数据模型：

```python
def parse_document(
    response: DownloadResponse,
    rules: ParserRules,
) -> ParsedDocument:
    ...
```

复杂函数应拆分为：

* 参数校验；
* 核心处理；
* 结果构建；
* 错误转换。

不得使用布尔参数控制多个完全不同的执行路径。

例如，应避免：

```python
process_page(page, save=True, parse=True, score=False, export=True)
```

---

## 5. Python 数据模型

跨模块传递的数据不得长期使用结构不明确的嵌套字典。

简单内部数据可以使用字典。

以下场景应使用明确的数据模型：

* 任务请求；
* 搜索结果；
* 下载结果；
* 解析结果；
* 标准文档；
* 附件；
* 错误信息；
* 评分结果；
* 存储结果。

数据模型应明确：

* 必填字段；
* 可选字段；
* 默认值；
* 字段类型；
* 时间格式；
* 扩展字段。

模型转换应集中处理，不得在多个模块重复转换。

---

## 6. Python 异步与并发

异步代码只用于确实存在大量 I/O 等待的场景。

不得为了形式统一，将所有函数改为异步。

异步代码必须：

* 设置超时；
* 限制并发；
* 正确取消任务；
* 正确关闭客户端；
* 处理部分失败；
* 避免无限创建协程；
* 避免阻塞调用混入事件循环。

使用线程或进程前，应明确：

* 是否为 I/O 密集型；
* 是否为 CPU 密集型；
* 是否需要共享状态；
* 是否存在资源竞争；
* 是否需要进程隔离。

并发数量必须来自配置，不得硬编码。

## 7. Go 版本与代码风格

Go 版本应在 `go.mod` 中统一声明。

Go 代码必须：

* 通过 `gofmt`；
* 通过项目要求的静态检查；
* 使用清晰的包名；
* 避免包名重复表达目录含义；
* 避免循环依赖；
* 避免全局可变状态；
* 避免在 `init()` 中执行复杂业务逻辑；
* 避免无意义接口；
* 保持错误链。

命名规范：

* 包名：小写、简短；
* 导出标识符：`PascalCase`；
* 非导出标识符：`camelCase`；
* 接口根据职责命名；
* 常量名称表达真实含义。

接口应由调用方定义，而不是为了抽象而提前创建大量接口。

---

## 8. Go 函数与方法设计

Go 函数应：

* 参数明确；
* 返回值明确；
* 错误作为最后一个返回值；
* 保留原始错误信息；
* 避免修改隐藏的全局状态；
* 避免承担多个业务阶段。

示例：

```go
func (s *TaskService) CreateTask(
    ctx context.Context,
    input CreateTaskInput,
) (*Task, error) {
    // ...
}
```

涉及以下操作时，应接收 `context.Context`：

* 数据库访问；
* HTTP 请求；
* Redis；
* 文件操作；
* Worker 调用；
* 长时间运行的任务。

不得用 `context.Background()` 替代已有调用上下文。

---

## 9. Go 错误处理

不得忽略 Go 错误。

禁止：

```go
value, _ := doSomething()
```

除非明确证明该错误不可能发生，并附有说明。

错误应保留上下文：

```go
return fmt.Errorf("load site config %q: %w", siteName, err)
```

不得只返回模糊错误：

```go
return errors.New("failed")
```

服务层应将底层错误转换为可理解的业务错误，但必须保留原始错误链。

HTTP 层负责将业务错误映射为状态码，不得在底层模块直接拼装 HTTP 响应。

---

## 10. Go 并发规范

启动 Goroutine 前必须明确：

* 谁负责结束；
* 如何传递取消信号；
* 如何回收资源；
* 如何处理 panic；
* 如何收集错误；
* 是否存在共享数据竞争。

禁止无限制启动 Goroutine。

并发任务应使用：

* 上下文取消；
* 有界 Worker Pool；
* 明确的 Channel 生命周期；
* WaitGroup 或等价同步机制；
* 必要的互斥保护。

Channel 的关闭通常由发送方负责。

不得通过 `time.Sleep()` 解决同步问题。

---

## 11. 包与模块边界

包应围绕明确职责划分。

禁止创建承载所有内容的通用包，例如：

```text
utils
common
helper
misc
```

如果确实存在此类目录，应确保其中每个文件职责明确，并逐步拆分。

推荐按能力划分：

```text
config
logging
search
download
parser
cleaner
storage
task
worker
```

不得为了复用少量代码创建跨越多个业务层的大型公共模块。

公共模块必须稳定、职责单一，并具备测试。

---

## 12. HTTP 客户端规范

项目应统一使用封装后的 HTTP 客户端。

业务模块不得各自创建完整 HTTP 实现。

统一 HTTP 客户端负责：

* 超时；
* 重试；
* 重定向；
* Header；
* User-Agent；
* Cookie；
* 代理；
* TLS；
* 限流；
* 响应大小限制；
* 日志；
* 指标；
* 错误转换。

网站特有请求参数由插件提供。

不得在业务代码中散落：

* 固定 Header；
* 固定 Cookie；
* 固定代理；
* 固定超时；
* 固定重试次数。

---

## 13. 接口设计规范

内部接口和外部接口都应保持稳定和明确。

接口定义必须说明：

* 输入；
* 输出；
* 必填字段；
* 可选字段；
* 错误；
* 超时；
* 重试行为；
* 幂等性；
* 版本兼容。

新增字段时，优先采用兼容方式。

删除或重命名字段前，必须确认所有调用方。

不得使用字段含义不明确的结构：

```json
{
  "data": {},
  "extra": {},
  "other": {}
}
```

字段名应表达真实业务含义。

---

## 14. JSON 与时间格式

跨语言通信统一使用 JSON。

JSON 字段统一使用 `snake_case`。

例如：

```json
{
  "task_id": "task-001",
  "created_at": "2026-07-26T10:30:00Z",
  "retry_count": 1
}
```

时间统一使用 ISO 8601 / RFC 3339 格式。

跨服务传输时应包含时区。

数据库存储时间应优先使用 UTC。

展示层根据用户时区进行转换。

不得在协议中混用：

* 秒级时间戳；
* 毫秒级时间戳；
* 本地时间字符串；
* 无时区时间。

## 15. 配置规范

配置按以下优先级加载：

```text
默认值
  ↓
配置文件
  ↓
.env
  ↓
操作系统环境变量
```

环境变量优先级最高。

配置应按照模块组织：

```yaml
server:
  host: ""
  port: 8080

http:
  timeout_seconds: 30
  retry_count: 3

redis:
  address: ""

database:
  driver: ""
  dsn: ""

worker:
  concurrency: 4
```

配置加载应集中处理。

业务模块只接收已解析、已校验的配置对象。

配置启动时必须校验。

关键配置缺失时应立即失败，不得运行到业务阶段才报错。

---

## 16. 密钥与敏感配置

以下内容不得写入普通配置文件或代码：

* API Key；
* Token；
* Cookie；
* 密码；
* 私钥；
* 证书密码；
* 数据库生产凭据。

敏感配置应使用环境变量或专门的密钥管理方式。

示例配置中使用占位符：

```text
YOUR_API_KEY
YOUR_DATABASE_DSN
```

日志中不得输出完整密钥。

必要时只显示脱敏值。

---

## 17. 日志规范

Python 和 Go 应使用结构化日志。

日志字段建议包括：

```text
timestamp
level
service
module
task_id
worker_id
site
provider
stage
url
duration_ms
error_code
message
```

不是每条日志都必须包含所有字段，但任务相关日志应尽量包含 `task_id`。

日志级别：

* `DEBUG`：开发调试信息；
* `INFO`：正常关键流程；
* `WARN`：可恢复异常或降级；
* `ERROR`：当前操作失败；
* `FATAL`：服务无法继续运行。

禁止在循环中无控制输出大量日志。

禁止重复记录同一个错误的完整堆栈。

错误应在最有处理能力的边界记录一次完整信息。

---

## 18. 错误分类

错误至少分为：

* 配置错误；
* 参数错误；
* 网络错误；
* 下载错误；
* 解析错误；
* 数据校验错误；
* 存储错误；
* 权限错误；
* 外部服务错误；
* 系统内部错误。

错误对象建议包含：

```text
code
message
stage
retryable
cause
details
```

错误代码必须稳定。

错误消息用于人类理解。

不得让调用方通过匹配错误字符串判断错误类型。

---

## 19. 重试规范

只有明确可恢复的错误才能自动重试。

重试应具备：

* 最大次数；
* 退避策略；
* 超时；
* 抖动；
* 错误分类；
* 日志；
* 指标。

禁止无限重试。

禁止对以下错误自动重试：

* 配置缺失；
* 参数错误；
* 鉴权失败；
* 插件不存在；
* 解析规则错误；
* 数据模型不合法。

任务重试和单次 HTTP 请求重试应区分处理，避免重复放大请求数量。

---

## 20. 数据库访问规范

数据库访问必须集中在 Repository、Storage 或 DAO 层。

以下模块不得直接执行 SQL：

* Handler；
* Parser；
* Cleaner；
* Scorer；
* Search Provider；
* Site Plugin。

数据库操作应：

* 使用参数化查询；
* 正确传递上下文；
* 设置超时；
* 检查返回错误；
* 明确事务边界；
* 避免 N+1 查询；
* 避免无条件查询全部字段；
* 避免一次加载无限记录；
* 使用分页或批处理。

任何数据库结构变化都必须通过迁移文件完成。

---

## 21. 事务规范

事务只覆盖必须保持一致的操作。

不得将以下操作长时间放在数据库事务内：

* 外部 HTTP 请求；
* 文件下载；
* AI API 调用；
* OCR；
* 长时间计算；
* 等待队列。

事务内发生错误时必须回滚。

不得忽略提交或回滚错误。

跨服务流程不得假设可以依赖单个数据库事务完成，应设计明确状态和补偿机制。

---

## 22. DuckDB 使用规范

DuckDB 用于：

* 离线分析；
* 数据统计；
* 报表；
* Parquet 查询；
* 数据质量检查；
* 批处理。

DuckDB 不用于：

* 多进程高并发核心业务写入；
* 用户权限状态；
* 实时任务状态；
* 分布式事务；
* Redis 替代品；
* 主业务事实来源。

DuckDB 文件路径应配置化。

分析任务应避免与核心采集流程争用大量 CPU、内存和磁盘。

---

## 23. Redis 使用规范

Redis 用于：

* 队列；
* 缓存；
* 分布式锁；
* 限流；
* 幂等；
* 临时状态；
* Worker 心跳。

Redis 中的数据应明确：

* Key 命名；
* Value 格式；
* TTL；
* 删除策略；
* 是否可重建。

推荐 Key 格式：

```text
project:module:resource:id
```

例如：

```text
collector:task:lock:task-001
collector:worker:heartbeat:worker-01
```

不得把 Redis 作为唯一长期数据源。

---

## 24. 文件存储规范

原始文件应按照稳定目录保存。

建议路径包含：

* 日期；
* 来源；
* 文件 Hash；
* 文件类型。

例如：

```text
storage/raw/2026/07/26/example.gov.cn/abc123.html.gz
```

数据库保存：

* 逻辑路径；
* Hash；
* 文件大小；
* MIME；
* 来源 URL；
* 关联记录。

写文件时应：

* 使用临时文件；
* 完成后原子重命名；
* 防止路径穿越；
* 校验文件大小；
* 必要时校验 Hash；
* 正确关闭文件。

---

## 25. 插件开发规范

每个插件必须具备：

* 唯一名称；
* 插件类型；
* 版本；
* 配置定义；
* 输入类型；
* 输出类型；
* 错误类型；
* 支持范围；
* 独立测试。

插件不得：

* 直接读取全局配置文件；
* 直接创建数据库连接；
* 直接操作 Redis；
* 修改其他插件状态；
* 在导入阶段执行任务；
* 吞掉异常；
* 返回未定义结构。

插件依赖通过构造参数或统一上下文传入。

## 26. 网站规则规范

优先使用配置描述网站差异，例如：

* 域名；
* 搜索入口；
* URL 规则；
* XPath；
* CSS Selector；
* 日期格式；
* 字段映射；
* 附件规则；
* 请求 Header。

只有配置无法表达时，才新增网站专用代码。

网站专用代码不得复制：

* HTTP 客户端；
* 日志初始化；
* 配置加载；
* 通用正文清洗；
* 数据库存储；
* 重试机制。

网站规则必须至少包含一个真实页面测试样例或固定测试夹具。

## 27. 测试分层

测试分为：

### 单元测试

验证单个函数、类或模块。

特点：

* 快；
* 稳定；
* 不依赖外网；
* 不依赖生产数据库；
* 可重复执行。

### 集成测试

验证多个模块协作，例如：

* Go 与数据库；
* Python 与本地测试服务；
* Redis 队列；
* Go 与 Python 通信；
* 插件注册和调用。

### 契约测试

验证 Python 与 Go 的协议兼容：

* 字段名称；
* 字段类型；
* 必填字段；
* 状态值；
* 错误结构；
* 时间格式。

### 端到端测试

验证完整流程：

```text
创建任务
  ↓
执行搜索
  ↓
下载页面
  ↓
解析内容
  ↓
保存结果
  ↓
返回状态
```

端到端测试数量应少于单元测试。

---

## 28. 测试要求

每次修改必须补充或更新对应测试。

修复 Bug 时，应优先增加能够复现 Bug 的测试，再修复代码。

测试不得依赖：

* 当前时间的偶然结果；
* 随机外网内容；
* 固定执行顺序；
* 本地个人路径；
* 生产凭据；
* 其他测试遗留状态。

需要随机数据时，应设置固定种子或验证稳定性质。

测试名称应表达场景和预期结果。

---

## 29. 外部网站测试

单元测试不得直接请求真实外部网站。

应使用：

* 固定 HTML；
* 固定 JSON；
* 本地 HTTP 测试服务器；
* Mock；
* 录制并脱敏的响应；
* 测试夹具。

真实网站验证应作为独立手动测试或受控集成测试。

真实网站变化不得导致普通单元测试随机失败。

---

## 30. 测试命令

Python 项目至少应支持：

```bash
pytest
```

如果项目已配置对应工具，还应运行：

```bash
ruff check .
mypy .
```

Go 项目至少应支持：

```bash
go test ./...
go vet ./...
```

涉及并发修改时，建议运行：

```bash
go test -race ./...
```

具体命令以项目已有配置为准。

不得为了满足文档而强行引入尚未使用的工具。

---

## 31. Mock 使用规范

只 Mock 外部边界：

* HTTP；
* 数据库；
* Redis；
* 文件系统；
* 时间；
* 第三方 API；
* AI 服务。

不要过度 Mock 内部业务逻辑。

测试应尽量验证真实模块协作，而不是只验证 Mock 调用了几次。

Mock 返回结构必须与真实接口一致。

---

## 32. 性能规范

性能优化必须基于实际测量。

优化前应明确：

* 当前耗时；
* 数据规模；
* 性能瓶颈；
* 目标指标；
* 测试方法。

禁止仅凭猜测进行复杂优化。

重点关注：

* 无限并发；
* 重复下载；
* 重复解析；
* N+1 查询；
* 大对象复制；
* 一次加载全部数据；
* 无限制日志；
* 无限制重试；
* 大文件常驻内存。

---

## 33. 依赖管理

新增依赖前应确认：

* 标准库能否解决；
* 项目已有依赖能否解决；
* 依赖是否持续维护；
* 许可证是否适合；
* 是否引入大量间接依赖；
* 是否影响部署；
* 是否存在安全风险。

禁止为了一个简单函数引入大型框架。

依赖版本应记录在项目依赖文件中。

不得只在开发者本地安装而不更新依赖声明。

---

## 34. 代码注释

注释应解释：

* 为什么这样设计；
* 为什么需要特殊处理；
* 外部协议限制；
* 不明显的边界条件；
* 临时兼容方案；
* 安全原因；
* 性能原因。

注释不应重复代码表面含义。

避免：

```python
# 增加计数
count += 1
```

临时方案必须标明：

* 原因；
* 影响；
* 后续处理条件。

---

## 35. 文档字符串与公开 API

公共 Python 函数、类和模块应在必要时提供文档字符串。

公开 Go 类型、函数、方法应遵守 Go 文档注释习惯。

文档应说明：

* 用途；
* 关键参数；
* 返回值；
* 错误；
* 副作用；
* 并发安全性；
* 示例或限制。

内部简单函数不要求机械添加无价值注释。

---

## 36. Git 分支与提交

每个独立任务建议使用独立分支。

分支名建议：

```text
feature/通用功能
fix/问题描述
refactor/模块名称
docs/文档内容
test/测试内容
```

每次提交应保持：

* 范围单一；
* 能够构建；
* 测试通过；
* 提交信息明确；
* 不包含敏感信息；
* 不包含无关生成文件。

AI 不得自行执行 `git push`。

---

## 37. 提交信息规范

提交信息应说明修改类型和内容。

示例：

```text
feat(search): add unified provider interface
fix(parser): handle missing publish time
test(storage): add duplicate document cases
docs(architecture): document worker protocol
```

提交信息不得使用：

```text
update
fix bug
changes
done
```

除非项目已经采用其他明确规范，应遵守项目现有规范。

---

## 38. Code Review 检查项

代码审查至少检查：

* 是否满足当前任务；
* 是否超出修改范围；
* 是否破坏架构边界；
* Python 与 Go 职责是否混淆；
* 是否重复实现已有能力；
* 是否修改公共接口；
* 是否处理错误；
* 是否正确记录日志；
* 是否存在并发风险；
* 是否存在资源泄漏；
* 是否存在安全问题；
* 是否更新测试；
* 是否更新文档；
* 是否包含敏感信息；
* 测试是否真实有效。

审查结论建议分为：

```text
必须修复
建议修复
可以接受
```

---

## 39. AI 输出规范

AI 完成代码任务后，应输出：

### 修改文件

列出所有新增、修改和删除的文件。

### 修改摘要

说明每个文件完成了什么。

### 测试结果

列出实际执行的命令和结果。

不得声称未执行的测试已经通过。

### 兼容性

说明是否影响：

* API；
* 配置；
* 数据库；
* 数据模型；
* 部署；
* Python 与 Go 通信。

### 剩余风险

说明：

* 未覆盖场景；
* 未执行测试；
* 外部依赖；
* 后续建议。

---

## 40. 完成标准

开发任务只有同时满足以下条件才算完成：

* 当前需求已实现；
* 未扩大修改范围；
* 代码符合现有架构；
* 格式化完成；
* 静态检查完成或明确说明未运行；
* 相关测试通过；
* 新行为有测试覆盖；
* 错误处理完整；
* 日志可定位；
* 公共接口保持兼容或已明确变更；
* 配置和文档已同步；
* `git diff` 中没有无关修改；
* 没有提交敏感信息；
* 剩余风险已明确说明。
