# SYSTEM_ARCHITECTURE.md

> 本文档描述通用信息采集平台的总体架构、模块边界、数据流和扩展方式。
>
> 所有具体实现必须遵守项目根目录中的 `AGENTS.md`。
>
> 本文档描述目标架构，不代表所有模块已经完成实现。

---

## 1. 系统定位

本项目不是针对某一个固定网站开发的采集程序，而是一个可扩展的通用信息采集平台。

系统应逐步支持：

* 多种网站类型；
* 多种搜索入口；
* 静态页面和动态页面；
* HTML、PDF、Word、图片等内容；
* 可配置采集规则；
* 可插拔解析器；
* 可插拔搜索提供者；
* 可插拔清洗、评分和导出模块；
* 任务调度与并发执行；
* 结构化数据存储；
* 离线分析和统计。

系统设计的核心目标是：

* 新增网站时尽量不修改核心模块；
* 新增搜索源时不影响现有搜索逻辑；
* Python 与 Go 职责清晰；
* 业务数据与分析数据分离；
* 原始文件与数据库数据分离；
* 模块之间通过稳定接口协作。

---

## 2. 总体架构

系统采用 Python 与 Go 协作的双核心架构。

```text
用户或管理端
      │
      ▼
Go API 服务
      │
      ├── 配置管理
      ├── 任务管理
      ├── 调度管理
      ├── Worker 管理
      ├── 状态管理
      └── 数据持久化
      │
      ▼
任务队列或内部调用协议
      │
      ▼
Python 采集 Worker
      │
      ├── 搜索
      ├── 下载
      ├── 解析
      ├── 清洗
      ├── 标准化
      ├── 评分
      ├── 去重
      ├── AI 分析
      └── 文件处理
      │
      ▼
结构化结果与原始文件
      │
      ├── 事务数据库
      ├── Redis
      ├── DuckDB
      └── 文件系统或对象存储
```

Go 负责平台运行和业务状态。

Python 负责网页内容处理和采集算法。

两者之间通过明确的数据协议通信，不直接依赖对方内部实现。

## 3. 系统职责边界

### 3.1 Go 服务职责

Go 负责平台层能力，包括：

* HTTP API；
* 管理端接口；
* 采集任务创建；
* 任务调度；
* 任务状态管理；
* Worker 注册与管理；
* 并发控制；
* 用户与权限；
* 配置管理；
* 数据持久化；
* 任务重试控制；
* 服务健康检查；
* 运行状态监控；
* 数据库事务；
* Redis 队列和分布式协调；
* Python Worker 生命周期管理。

Go 不负责：

* HTML DOM 解析；
* XPath 或 CSS Selector 提取；
* 正文识别；
* 文本清洗；
* 内容评分；
* OCR；
* NLP；
* 网站页面结构判断；
* 搜索结果页面解析。

### 3.2 Python Worker 职责

Python 负责采集和内容处理能力，包括：

* 搜索入口调用；
* 搜索结果解析；
* HTTP 页面下载；
* 请求重试和页面编码识别；
* HTML 解析；
* XPath 和 CSS Selector；
* 正文抽取；
* 标题、作者、时间和来源提取；
* 文本清洗；
* 数据标准化；
* URL 规范化；
* 内容指纹计算；
* 去重判断；
* 内容质量评分；
* 关键词扩展；
* 分类、摘要和实体识别；
* PDF、Word、Excel、图片等文件解析；
* OCR；
* 网站插件执行；
* 解析失败原因输出。

Python 不直接管理：

* 用户权限；
* 平台级任务调度；
* 系统级事务；
* 管理端 API；
* Go 服务内部状态；
* 生产环境数据库迁移。

## 4. 核心数据流

系统主数据流保持单向：

```text
任务创建
  ↓
任务调度
  ↓
搜索发现
  ↓
URL 标准化
  ↓
页面下载
  ↓
内容解析
  ↓
文本清洗
  ↓
字段标准化
  ↓
内容评分
  ↓
数据去重
  ↓
结果存储
  ↓
统计分析
  ↓
数据导出
```

每个阶段只处理自己的职责，不应跨越多个层级完成无关工作。

例如：

* 下载器不解析正文；
* 解析器不直接写数据库；
* 清洗器不创建任务；
* 评分器不修改原始文件；
* 存储模块不重新下载网页；
* API 层不实现采集算法。

某一阶段失败时，应返回明确的失败状态和错误信息，由上层决定是否重试、跳过或终止。

## 5. 系统分层

系统逻辑分为以下层级：

```text
Interface
    ↓
Application
    ↓
Domain
    ↓
Plugin
    ↓
Infrastructure
```

### 5.1 Interface 层

负责系统入口，包括：

* HTTP API；
* 命令行入口；
* 管理界面；
* 外部系统调用入口。

Interface 层只负责：

* 参数接收；
* 参数校验；
* 调用应用服务；
* 返回结果。

不得在 Interface 层实现核心采集逻辑。

### 5.2 Application 层

负责组织业务流程，包括：

* 创建采集任务；
* 启动采集流程；
* 控制任务状态；
* 调用搜索、下载、解析和存储能力；
* 处理阶段性失败；
* 汇总执行结果。

Application 层负责流程编排，不负责具体算法。

### 5.3 Domain 层

负责系统核心数据模型和业务规则，包括：

* 采集任务；
* 网站定义；
* 搜索请求；
* 页面记录；
* 文档记录；
* 附件记录；
* 采集结果；
* 失败记录；
* 评分结果；
* 去重结果。

Domain 层不应依赖具体数据库、HTTP 库或第三方平台。

### 5.4 Plugin 层

负责可替换、可扩展的功能实现，包括：

* 搜索提供者；
* 网站插件；
* 下载器；
* 解析器；
* 清洗器；
* 评分器；
* 去重器；
* AI 提供者；
* OCR 提供者；
* 导出器；
* 存储适配器。

插件应通过统一接口注册和调用。

### 5.5 Infrastructure 层

负责具体基础设施，包括：

* PostgreSQL 或 MySQL；
* Redis；
* DuckDB；
* 文件系统；
* 对象存储；
* HTTP 客户端；
* 浏览器自动化；
* 日志系统；
* 配置加载；
* 外部 API；
* 消息队列。

业务模块不应直接依赖基础设施实现细节。

## 6. 核心模块

### 6.1 Task 模块

负责任务定义和执行状态。

任务至少应包含：

* 任务 ID；
* 任务类型；
* 网站或来源；
* 搜索关键词；
* 创建时间；
* 开始时间；
* 完成时间；
* 当前状态；
* 重试次数；
* 错误信息；
* 执行参数；
* 结果统计。

推荐任务状态：

```text
pending
running
succeeded
partially_succeeded
failed
cancelled
```

任务状态由 Go 服务统一维护。

### 6.2 Search 模块

负责发现候选 URL。

搜索来源可以包括：

* TRS；
* JPAAS；
* 通用站内搜索；
* 搜索引擎；
* 网站 API；
* RSS；
* Sitemap；
* 列表页；
* 自定义搜索接口。

所有搜索提供者必须实现统一接口。

统一输入至少包含：

* 关键词；
* 时间范围；
* 页码；
* 每页数量；
* 网站范围；
* 扩展参数。

统一输出至少包含：

* URL；
* 标题；
* 摘要；
* 来源；
* 发布时间；
* 搜索排名；
* 扩展元数据。

Search 模块只负责发现候选内容，不负责正文解析。

### 6.3 URL Normalizer 模块

负责 URL 标准化，包括：

* 相对地址转绝对地址；
* 移除无意义跟踪参数；
* 统一协议和域名格式；
* 规范化路径；
* 处理锚点；
* 判断重复 URL；
* 生成 URL 指纹。

URL 标准化应发生在下载之前。

### 6.4 Downloader 模块

负责获取网页和文件。

Downloader 应处理：

* 超时；
* 重试；
* 重定向；
* 状态码；
* 编码；
* Cookie；
* Header；
* 代理；
* 限速；
* 文件大小限制；
* MIME 类型；
* 响应元数据；
* 静态页面；
* 必要时的动态页面。

Downloader 输出原始响应，不负责提取正文。

### 6.5 Parser 模块

负责从原始内容中提取结构化字段。

Parser 可能包括：

* HTML Parser；
* JSON Parser；
* PDF Parser；
* Word Parser；
* Excel Parser；
* Image Parser；
* RSS Parser；
* API Response Parser。

标准输出建议包含：

* 标题；
* 正文；
* 作者；
* 来源；
* 发布时间；
* 栏目；
* 文号；
* 附件；
* 图片；
* 页面元数据；
* 原始字段；
* 解析置信度；
* 解析警告。

Parser 不直接执行数据库写入。

### 6.6 Cleaner 模块

负责对解析后的文本和字段进行清洗，包括：

* 去除无意义空白；
* 去除导航和页脚内容；
* 统一换行；
* 统一标点；
* 修复乱码；
* 统一时间格式；
* 统一字段格式；
* 清理重复段落；
* 清理无效标签；
* 保留必要结构。

Cleaner 不负责下载页面，也不负责调度任务。

### 6.7 Normalizer 模块

负责将不同来源的数据转换为统一数据模型。

标准化内容可以包括：

* 时间；
* 来源名称；
* 网站域名；
* 文档类型；
* 作者；
* 栏目；
* 文号；
* 附件格式；
* URL；
* 语言；
* 地区；
* 扩展元数据。

网站特有字段应保存在扩展元数据中，不应频繁修改核心数据模型。

### 6.8 Scorer 模块

负责评估数据质量和相关性，包括：

* 标题完整度；
* 正文完整度；
* 时间可信度；
* 来源可信度；
* 关键词相关性；
* 内容长度；
* 重复程度；
* 解析置信度；
* 附件完整度。

评分结果应包含：

* 总分；
* 分项得分；
* 评分原因；
* 评分版本。

Scorer 不应直接修改原始文本。

### 6.9 Deduplicator 模块

负责识别重复数据。

可使用：

* 标准化 URL；
* URL Hash；
* 正文 Hash；
* 标题 Hash；
* SimHash；
* MinHash；
* 标题与时间组合；
* 来源和文号组合。

去重结果应区分：

* 完全重复；
* 内容重复；
* URL 重复；
* 高度相似；
* 不重复。

原始记录不应因去重判断而直接丢失，应保留必要的来源关系和审计信息。

### 6.10 Storage 模块

负责统一数据存储。

业务模块必须通过 Storage 接口访问数据，不应在解析器、清洗器或评分器中直接编写 SQL。

Storage 至少应提供：

* 创建任务；
* 更新任务状态；
* 保存搜索结果；
* 保存页面记录；
* 保存文档记录；
* 保存附件记录；
* 保存失败记录；
* 查询重复记录；
* 保存评分结果；
* 查询采集历史。

### 6.11 Analysis 模块

负责离线统计和数据分析，包括：

* 站点成功率；
* 采集数量；
* 失败类型；
* 页面更新时间；
* 内容重复率；
* 质量评分分布；
* 关键词命中率；
* 来源分布；
* 任务耗时；
* 下载性能；
* 解析性能。

分析任务不应阻塞核心采集流程。

### 6.12 Exporter 模块

负责数据导出。

支持形式可以包括：

* JSON；
* JSON Lines；
* CSV；
* Excel；
* Parquet；
* 数据库同步；
* API 推送。

导出器只能读取标准化后的数据模型，不应依赖某个网站的内部字段结构。

## 7. 插件体系

系统采用插件化扩展方式。

以下能力应支持插件化：

```text
Search Provider
Site Plugin
Downloader
Parser
Cleaner
Normalizer
Scorer
Deduplicator
AI Provider
OCR Provider
Exporter
Storage Adapter
```

插件必须：

* 实现统一接口；
* 提供唯一名称；
* 提供版本信息；
* 声明支持的内容类型；
* 声明必要配置；
* 返回统一结果；
* 返回明确错误；
* 支持独立测试。

插件不得：

* 修改核心全局状态；
* 绕过统一日志；
* 绕过统一配置；
* 直接操作其他插件内部数据；
* 在模块导入时执行采集任务；
* 将密钥硬编码在代码中。

---

## 8. 网站插件

网站插件用于处理特定网站的差异。

一个网站插件可以包含：

```text
site plugin
├── site metadata
├── search adapter
├── URL rules
├── request rules
├── parser rules
├── cleaner rules
├── attachment rules
└── validation rules
```

网站插件应尽量只描述网站差异。

能够由通用模块完成的功能，不应在网站插件中重复实现。

新增网站时，优先顺序为：

1. 使用通用搜索模块；
2. 使用通用下载器；
3. 使用通用解析器；
4. 使用配置化规则；
5. 仅在通用能力无法满足时新增网站专用逻辑。

网站插件不应成为一套独立采集系统。

---

## 9. 搜索提供者插件

每一种搜索来源应实现统一的 Search Provider 接口。

例如：

```text
search providers
├── trs
├── jpaas
├── site_search
├── sitemap
├── rss
└── custom_api
```

新增搜索提供者时：

* 不修改任务模型；
* 不修改解析器；
* 不修改存储模块；
* 不复制现有 HTTP 客户端；
* 不复制配置加载逻辑；
* 只实现统一接口和来源特有逻辑。

业务层通过提供者名称或配置选择搜索实现。

## 10. 通信协议

Go 与 Python 之间必须通过稳定协议通信。

可采用：

* HTTP；
* 本地进程标准输入输出；
* 消息队列；
* RPC；
* 任务文件协议。

无论采用哪种方式，都应使用统一请求和响应结构。

任务请求至少包含：

```json
{
  "task_id": "string",
  "task_type": "string",
  "provider": "string",
  "site": "string",
  "parameters": {},
  "created_at": "datetime"
}
```

任务响应至少包含：

```json
{
  "task_id": "string",
  "status": "string",
  "data": {},
  "errors": [],
  "metrics": {},
  "completed_at": "datetime"
}
```

错误结构至少包含：

```json
{
  "code": "string",
  "message": "string",
  "stage": "string",
  "retryable": false,
  "details": {}
}
```

协议字段变更必须考虑向后兼容。

## 11. 数据存储架构

系统存储分为四类。

### 11.1 事务数据库

事务数据库使用 PostgreSQL 或 MySQL。

负责保存：

* 网站配置；
* 搜索源配置；
* 采集任务；
* 任务状态；
* 页面元数据；
* 文档元数据；
* 附件元数据；
* 用户与权限；
* 失败记录；
* 去重关系；
* 评分结果；
* 审计信息。

事务数据库是业务状态的主要事实来源。

### 11.2 Redis

Redis 负责：

* 任务队列；
* 短期状态；
* 分布式锁；
* 限流；
* 临时缓存；
* Worker 心跳；
* 幂等控制。

Redis 不作为长期业务数据的唯一存储。

### 11.3 DuckDB

DuckDB 负责：

* 本地分析；
* 批量统计；
* 数据质量分析；
* 去重分析；
* 报表计算；
* Parquet 和 CSV 查询；
* 离线数据处理；
* 开发环境数据检查。

DuckDB 不作为多进程并发写入的核心业务状态库。

### 11.4 文件系统或对象存储

负责保存：

* 原始 HTML；
* PDF；
* Word；
* Excel；
* 图片；
* 附件；
* 压缩包；
* 原始响应；
* 大型导出文件。

事务数据库只保存：

* 文件路径或对象地址；
* 文件 Hash；
* MIME 类型；
* 文件大小；
* 来源 URL；
* 创建时间；
* 关联记录；
* 必要元数据。

## 12. 标准数据模型

系统内部应使用统一文档模型。

标准文档建议包含：

```text
Document
├── id
├── url
├── canonical_url
├── source
├── source_domain
├── site_id
├── title
├── content
├── author
├── published_at
├── crawled_at
├── document_type
├── category
├── document_number
├── language
├── region
├── content_hash
├── quality_score
├── attachments
├── metadata
└── raw_file_reference
```

不同网站的特殊字段应放入 `metadata`。

只有被多个来源长期共同使用的字段，才考虑进入核心模型。

## 13. 错误与重试

系统应根据错误类型决定是否重试。

可以重试的错误包括：

* 网络超时；
* 临时连接失败；
* HTTP 429；
* 部分 HTTP 5xx；
* 临时代理故障；
* Worker 短暂不可用；
* 外部服务限流。

通常不应自动重试的错误包括：

* 配置缺失；
* 认证信息错误；
* 解析规则无效；
* 请求参数错误；
* 不支持的文件格式；
* 数据校验失败；
* 插件不存在。

每次失败必须记录：

* 任务 ID；
* 阶段；
* 错误类型；
* 错误信息；
* 是否可重试；
* 当前重试次数；
* 相关 URL；
* 插件名称；
* 时间。

---

## 14. 可观测性

系统应记录以下指标：

* 任务总数；
* 成功任务数；
* 失败任务数；
* 部分成功任务数；
* 搜索结果数量；
* 下载成功率；
* 解析成功率；
* 去重数量；
* 平均质量评分；
* 平均任务耗时；
* 各阶段耗时；
* 各网站失败率；
* 各插件错误数量；
* Worker 状态；
* 队列长度。

日志、指标和任务状态应能通过 `task_id` 关联。

## 15. 新增网站流程

新增网站时，应按照以下顺序处理：

1. 分析网站搜索入口；
2. 判断是否可使用现有 Search Provider；
3. 判断是否可使用通用 Downloader；
4. 判断是否可使用通用 Parser；
5. 尝试使用配置化 XPath 或 CSS Selector；
6. 配置字段映射；
7. 配置清洗规则；
8. 配置附件处理规则；
9. 增加网站插件；
10. 增加插件单元测试；
11. 增加真实页面样例或测试夹具；
12. 验证标准数据模型输出；
13. 验证失败处理；
14. 验证重复采集结果；
15. 更新网站支持文档。

新增网站原则上不修改核心调度、存储和任务模型。

---

## 16. 新增搜索源流程

新增搜索来源时：

1. 创建新的 Search Provider；
2. 实现统一输入接口；
3. 实现统一输出模型；
4. 使用统一 HTTP 客户端；
5. 使用统一配置系统；
6. 使用统一日志系统；
7. 处理分页；
8. 处理限流；
9. 处理重试；
10. 增加单元测试；
11. 增加结果标准化测试；
12. 注册 Provider；
13. 更新支持列表。

新增搜索源不应修改具体网站解析器。

---

## 17. 新增解析器流程

新增内容类型或解析方式时：

1. 确定 MIME 类型或页面类型；
2. 实现统一 Parser 接口；
3. 输出标准文档模型；
4. 保留必要原始元数据；
5. 返回解析置信度；
6. 返回解析警告；
7. 增加成功样例；
8. 增加失败样例；
9. 增加边界测试；
10. 注册 Parser。

解析器不得直接创建任务或写入业务数据库。

---

## 18. 扩展决策原则

出现新需求时，按照以下顺序判断：

```text
现有配置能否解决？
        ↓
现有插件能否扩展？
        ↓
能否新增插件？
        ↓
能否新增通用接口实现？
        ↓
是否确实需要修改核心架构？
```

只有在现有配置、插件和接口都无法满足时，才考虑修改核心架构。

修改核心架构前，应先更新设计文档并经过人工确认。

## 20. 架构验收标准

系统架构应逐步达到以下结果：

* 新增网站主要通过配置或插件完成；
* 新增搜索源不修改业务流程；
* 下载器与解析器相互独立；
* 解析器不直接访问数据库；
* Python 和 Go 不重复实现相同能力；
* Go 统一维护任务状态；
* Python 统一负责内容处理；
* 事务数据和分析数据分离；
* 原始文件和结构化数据分离；
* 所有模块具有明确输入和输出；
* 插件能够独立测试；
* 错误能够定位到具体任务和阶段；
* 核心模块不依赖具体网站；
* 数据模型能够容纳不同网站结果；
* 系统支持逐步扩展，而不需要反复重写核心。
