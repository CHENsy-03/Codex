# DEVELOPMENT_RULES.md

> 本文件定义本仓库所有项目的通用开发、测试、审查和交付规则。
>
> 项目内部可以制定更具体的规则，但不得放宽本文件的底线要求。

---

## 1. 适用范围与优先级

本规则适用于仓库根目录和所有 `workspace/<project>` 子项目。

规则优先级：

1. 用户当前明确要求；
2. 仓库根目录 `AGENTS.md`；
3. 当前项目 `AGENTS.md`；
4. 本文件；
5. 当前项目 `docs/SYSTEM_ARCHITECTURE.md`；
6. 当前任务文档。

规则冲突时，应报告冲突，不得擅自选择对业务影响更大的方案。

---

## 2. 开始任务前

每次开始修改前必须：

- 阅读根目录和当前项目的 `AGENTS.md`；
- 阅读当前项目任务文档；
- 检查当前分支、HEAD、暂存区、工作区和未跟踪文件；
- 确认允许修改和禁止修改的范围；
- 理解调用关系、数据流和现有测试。

任务目标不清时，应先列出假设，不得擅自扩大范围。

---

## 3. 修改范围管理

每个任务只修改与当前需求直接相关的文件。

修改前应列出：

```text
文件路径
修改原因
预期变化
是否影响公共接口
是否需要新增测试
```

禁止：

- 顺手优化无关模块；
- 将格式调整混入功能修改；
- 批量移动目录；
- 替换技术框架；
- 升级无关依赖；
- 重写正常工作的模块；
- 修改任务未涉及的公共接口。

必须修改范围外文件时，应先停止并说明原因。

---

## 4. 代码风格与语言规范

各项目应在项目配置中统一声明：

- 运行时和工具链版本；
- 格式化工具；
- 静态检查工具；
- 测试命令；
- 命名约定。

代码必须：

- 使用明确、可读的命名；
- 为公共接口提供必要类型标注或文档；
- 避免隐藏的导入副作用；
- 避免全局可变状态；
- 避免在模块加载时执行网络、数据库或外部服务调用；
- 避免可变默认参数；
- 避免使用布尔参数控制多个完全不同的执行路径。

多语言项目应保持各语言既有工具链规范，不要求所有项目使用同一套语言栈。

---

## 5. 模块与职责边界

模块应围绕明确职责划分，禁止创建承载所有内容的通用包。

推荐按能力组织：

```text
config
logging
api
service
worker
storage
test
```

公共模块必须：

- 职责单一；
- 接口稳定；
- 有测试；
- 不跨多个业务层承担无关职责。

项目内部的模块边界应在项目架构文档中定义，根级规则不指定具体业务模块。

---

## 6. 数据、接口与兼容性

内部和外部接口都应保持稳定和明确。

接口定义应说明：

- 输入和输出；
- 必填和可选字段；
- 错误行为；
- 超时和重试；
- 幂等性；
- 版本兼容。

新增字段优先采用兼容方式。

删除或重命名字段前，必须确认所有调用方。

跨系统通信应统一：

- 序列化格式；
- 字段命名；
- 时间格式；
- 空值语义；
- 错误结构。

涉及数据库变更时，必须使用迁移方案，并保持旧数据可用。

---

## 7. 配置与秘密信息

配置应集中加载和校验，业务模块只接收已解析的配置对象。

配置优先级由项目定义，通常：

```text
默认值
配置文件
环境变量
```

以下内容不得写入代码或普通配置文件：

- API Key；
- Token；
- 密码；
- Cookie；
- 私钥；
- 证书；
- 数据库生产凭据。

敏感配置应使用环境变量或密钥管理服务。

日志、诊断、结果和错误信息不得输出完整秘密值。

示例配置只能使用占位符。

---

## 8. 日志与错误处理

日志应包含时间、级别、模块和可检索信息。

错误处理要求：

- 禁止忽略错误；
- 禁止使用无意义的 `except: pass`；
- 错误应包含原因、模块和可定位上下文；
- 错误信息不得包含秘密值；
- 网络、数据库和外部服务错误应转换为结构化错误；
- 错误应保留原始异常链。

不得在循环中无控制输出大量日志。

不得重复记录同一个错误的完整堆栈。

错误应在最有处理能力的边界记录一次完整信息。

---

## 9. 测试与验证

每次修改必须运行与修改相关的测试。

测试要求：

- 测试必须真实、可重复、可定位；
- 不得删除、跳过或弱化既有测试；
- 测试结果必须来自实际执行，不得预填或虚构；
- 单元测试不得依赖不稳定外部状态；
- 外部依赖应通过注入、Mock 或受控 fixture 隔离；
- 安全、失败路径和边界条件必须有测试；
- 不访问真实外部服务是默认约束，除非任务明确授权。

项目应定义统一测试命令，并尽可能运行全量测试。

静态检查、格式化和构建结果应真实记录。

---

## 10. Git 与工作区保护

所有开发工作必须保护用户预存修改。

Git 规则：

- 修改前记录当前分支、HEAD、暂存区、工作区和未跟踪文件；
- 不覆盖、不删除、不恢复用户已有修改；
- 不执行会覆盖用户文件的还原操作；
- 每个任务建议使用独立分支；
- 暂存和提交必须由开发者明确授权；
- AI 默认不得 push、创建 PR 或修改历史；
- 不使用破坏性 Git 命令清理工作区。

提交应保持范围单一、构建可用、测试通过、无敏感信息、无无关生成文件。

---

## 11. 文档同步

涉及以下变化时必须同步更新项目文档：

- 公共接口；
- 数据模型；
- 配置项；
- 模块结构；
- 运行方式；
- 任务状态。

禁止代码与文档不一致。

根级文档只记录多项目通用规范；项目实现细节、任务进度和测试数量应放在项目内部文档。

---

## 12. AI 与 Codex 协作

AI 和 Codex 在项目中执行任务时：

- 先阅读规则，再修改代码；
- 按最小修改原则执行；
- 不替代开发者做架构决策；
- 不擅自引入大型依赖；
- 不修改未经授权的文件；
- 出现阻塞立即停止并报告；
- 报告必须包含修改文件、测试结果、未执行测试、兼容性和剩余风险。

不得使用“全部正常”或“已经完成”代替真实证据。

---

## 13. Code Review

代码审查至少检查：

- 是否满足任务目标；
- 是否超出修改范围；
- 是否破坏模块边界；
- 是否修改公共接口；
- 是否处理错误；
- 是否存在并发或资源泄漏风险；
- 是否存在安全问题；
- 是否包含敏感信息；
- 是否更新测试；
- 是否更新文档；
- 测试是否真实有效。

审查结论建议分为：

```text
必须修复
建议修复
可以接受
```

---

## 14. 完成标准

任务完成必须同时满足：

- 当前需求已实现；
- 未扩大修改范围；
- 代码符合项目架构；
- 格式化和静态检查已执行或明确说明未执行；
- 相关测试通过；
- 新行为有测试覆盖；
- 错误处理完整；
- 日志可定位；
- 公共接口保持兼容或已明确变更；
- 配置和文档已同步；
- `git diff` 中没有无关修改；
- 没有提交敏感信息；
- 剩余风险已明确说明。

---

## 15. 阻塞处理

出现以下情况应立即停止：

- 任务目标不明确；
- 测试失败且无法确定修复方向；
- 架构或公共接口存在冲突；
- 必须扩大修改范围；
- 必须覆盖用户修改；
- 需要开发者确认关键业务规则。

停止报告必须包含：

- 当前执行步骤；
- 已完成修改；
- 修改文件列表；
- 错误日志；
- 阻塞原因；
- 建议交给开发者或上级设计者分析的问题。

不得通过猜测绕过阻塞。
